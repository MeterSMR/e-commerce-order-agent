## 一、产品定位与 V1\.0 范围

### 1\.1 目标用户与产品目标

本产品面向知道自己想玩的游戏和大致预算、但不熟悉硬件参数与游戏要求对应关系的消费者。用户用自然语言描述需求后，系统在本地可信数据和确定性规则约束下完成澄清、查询与校验，输出可核对的游戏本候选并解释不同方案的取舍。

V1\.0 同时验证两件事：

1. **用户能否获得满足必要条件、依据清楚且注明限制的选购建议；**

2. **单 Agent 在多轮交互和条件修改中，能否合理选择行动并始终受业务规则和运行上限约束。**

### 1\.2 支持的游戏与本地数据

V1\.0 仅支持以下 4 款游戏，且统一采用独立显卡准入要求：

|编号|游戏|V1\.0 已收录档位|

|GAME\-01|英雄联盟|最低配置（可用）、推荐配置（流畅）|
|GAME\-02|无畏契约|最低配置、推荐配置、高等配置|
|GAME\-03|原神|支持配置、推荐配置|

### 1\.3 版本边界

**本期V1\.0包含：**

1. 自然语言需求理解、硬条件与软偏好区分、动态必要澄清

2. 本地目录查询、硬条件筛选、四款游戏 6 维配置适配校验

3. 可信分批推荐（每批最多 3 款）、当前批比较、具体配置事实追问

4. 当前会话内条件修改与重新评估、无匹配/证据不足/异常反馈



本期不包含：

1. 实时联网搜索、比价、当前库存与实际成交价确认

2. 四款游戏以外的正式用途适配；实际画质、帧率和稳定性预测

3. 下单、支付、订单管理与售后；跨会话记忆；多 Agent 协作；全市场最优推荐

4. P1功能不作为 V1\.0 基础验收条件

## 二、用户场景、任务周期与结果分类

### 2\.1 核心场景

|编号|场景|用户示例|产品预期|
|---|---|---|---|
|S01|需求明确|“预算 10000 元以内，想玩英雄联盟，至少 16GB 内存”|直接提取条件，完成查询与校验后推荐|
|S02|需求模糊|“想买台游戏本，预算 9000 左右”|澄清想玩的具体游戏，不自行猜测配置|
|S03|多游戏需求|“主要玩无畏契约，偶尔玩原神”|不因“偶尔”就将原神判为非必要；影响资格且含义不明时先确认|
|S04|具体体验要求|“黑神话悟空能不能高画质稳定 60 帧？”|区分配置符合性与实际体验，说明限制并确认是否接受可验证范围|
|S05|商品比较|“这两台哪个更适合玩原神？”|基于已核实的配置、CPU/GPU 分数和适配依据解释差异|
|S06|条件修改|“预算改成 12000，其他不变”|保留未修改项，清空失效展示并重评受影响候选|
|S07|无法推荐|“预算 4000 以内，必须满足黑神话最低配置”|如实反馈无匹配或证据不足，不强行推荐|

### 2\.2 任务生命周期

- **同一任务内延续**：用户发起选购后的信息补充、条件修改、商品比较、追问、查看更多及手动重试，都属于同一个选购任务。一轮推荐完成（`R01`）或说明无法推荐（`R02`）只表示本轮结束，不新建任务，也不重置澄清次数，系统不主动连续追问或换批。

- **重新开始与结束**：用户明确要求“重新开始”或发起新任务时，清空原有条件、澄清次数、候选与已展示记录、比较选择及重试状态。用户明确结束时停止推进，之后再次选购按新任务处理。

- **页面刷新与关闭**：刷新或关闭页面后不恢复原任务，重新打开从空白状态开始。仅修改预算、游戏或偏好属于条件修改，会清空展示与比较记录，但不会重置本任务已使用的澄清次数。

### 2\.3 本轮结果分类

一轮选购或条件重评的结果分为四类。即使已有合格商品，如果还存在待用户确认的预算或体验范围事项，也不能直接判为 `R01`。

|编号|结果|判定条件|产品行为|
|---|---|---|---|
|R01|成功推荐|必要处理完成；至少 1 款通过全部必要校验且符合当前预算与用途判断范围；无待确认事项；推荐卡片已展示|每批展示最多 3 款商品卡片，支持比较、追问、查看更多和改条件|
|R02|无法推荐（业务原因）<br>|非执行故障，需明确说明具体原因：目录无匹配、需求不足或冲突（含澄清到限或拒绝）、商品事实或游戏依据不足、必要游戏或指定档位超出范围|说明具体原因与下一步可选操作，不强行推荐，不自动放宽条件；到限停问，仍允许用户主动补充|
|R03|等待用户补充或确认|存在影响判断的关键缺口或待确认事项，已在剩余额度内提出 1 个问题，用户尚未回复|暂停本轮推荐并等待回答，不重复提问；等待时间不计入 60 秒|
|R04|执行未完成（失败或超限）|模型调用、必要处理或结果生成失败或超限（包括校验已完成但结果生成超时）|停止本轮，不生成新的正式推荐，不表述为目录无匹配；提供手动重试入口|

结果统计时，`R01` 与 `R02` 分开计算。正常读取数据后发现字段缺失按 `UNKNOWN` 处理，不归为 `R04`；没有合格候选但仍存在关键状态 `UNKNOWN` 的潜在候选时，不能直接认定为“无匹配”。

## 四、功能需求与业务规则（P0）

### 4\.1 通用运行限制

以下上限由程序执行，各功能直接沿用：

|限制项|规则|
|---|---|
|澄清上限|同一任务最多 3 轮，每轮只提 1 个关键问题，不捆绑多问。含糊或无关回复也计入轮数；缺口、预算、体验范围和条件修改中的确认共用这 3 轮额度。用户拒绝提供必要信息时可提前停止；到限后按 `R02` 停止追问，但仍允许用户主动补充，且不重置次数|
|推荐分批|每批最多展示 3 款合格具体配置，不足不凑数、同批不重复。3 款只是展示上限，不能据此缩小查询和校验范围。仅用户主动请求“查看更多”时换批，全部展示完后保留当前批次，不循环回首批|
|候选比较|仅限当前批次内的 2–3 款（点击勾选或自然语言均可），不支持跨批比较。不足 2 款时不生成多款对比；换批或修改条件后清空选择和旧比较|
|时限与重试|单次处理上限 60 秒（不含等待用户回复）。LLM 或外部调用瞬时故障允许 Harness 静默重试 1 次；仍失败则报 `R04`，前端不自动重发，允许用户点击手动重试最多 1 次（重新计时）。用户重新输入自然语言按新请求处理|

### FR\-01｜需求理解与条件维护

|需求类型|用户示例|处理方式|
|---|---|---|
|预算硬条件|“预算不能超过 9000 元”|记录价格上限，参与硬条件校验|
|目标预算|“预算 9000 元左右”|优先选择预算内商品，无合适时再澄清，不自动转为硬上限|
|必要游戏|“主要玩英雄联盟”“两款都要能玩”|纳入必要游戏适配资格校验|
|非必要附加游戏|“偶尔玩原神，能兼顾更好”|不决定推荐资格，用于比较和限制披露|
|游戏配置档位|“希望达到原神推荐配置”|按已收录的对应游戏档位校验|
|明确硬件与设备限制|“内存至少 16GB”“重量不超 2kg”|记录对应上下限，参与硬条件校验|
|软偏好|“希望轻薄一点，性能好一些”|仅用于合格候选的排序、比较与解释，不转为硬条件|
|模糊需求|“希望玩游戏流畅点”|保留原意，判断是否需要澄清|

需求维护遵循以下规则：

- 硬条件必须由用户明确提出，“最好”“希望”“尽量”等倾向性表述归为软偏好。

- 使用频率不等于可放弃性，只有用户明确表示可以不满足时才归为附加游戏；含义不明且影响推荐资格时先确认。

- 不自行补充用户未确认的具体门槛（例如不能把“轻薄”自动定为 `≤ 1.5kg`）。

- 只有用户已提交的有效输入才会更新当前需求，并同步展示在页面条件摘要中。

### FR\-02｜动态必要澄清

|当前情况|处理方式|
|---|---|
|未明确具体游戏|询问想玩的游戏（并说明 V1\.0 支持的 4 款游戏）|
|条件存在明显冲突|指出冲突并请用户确认，不自行取舍|
|信息已充分，或只缺非必要偏好|直接进入查询与校验，不为用满额度提问|
|目标预算内无合适商品|说明当前预算下暂未找到合适机型，在剩余额度内询问是否提高预算或调整需求|
|提出高画质、稳定 60FPS 等具体体验要求|说明配置符合性与实际体验的区别，在剩余额度内确认是否接受当前可验证的范围|
|未指定游戏配置档位|默认采用该游戏已收录的最低档位，并在结果中说明|
|商品参数缺失|通过本地数据查询处理，不向用户索要商品硬件信息|
|信息已确认且仍有效|不重复询问|

用户一次给出多项信息时应一并吸收。第 3 轮答复如果补齐了关键信息，继续查询和校验；仍缺必要信息时停止追问，按 `R02` 说明缺口。

### FR\-03｜商品查询与硬条件筛选

以具体配置版本为单位查询 28 条本地商品。

**价格匹配规则**

|用户要求|校验与选取方式|
|---|---|
|硬上限（如“最高 9000 元”）|`price_max ≤ 上限` 判 `PASS`；`price_min > 上限` 判 `FAIL`；区间跨越上限（`price_min ≤ 上限 < price_max`）判 `UNKNOWN`，不进正式推荐并说明价格区间|
|硬下限（仅明确要求“不能低于 X 元”）|`price_min ≥ 下限` 判 `PASS`；`price_max < 下限` 判 `FAIL`；区间跨越下限判 `UNKNOWN`|
|目标预算（如“9000 元左右”）|优先选 `price_max ≤ 9000` 的合格商品；区间跨越目标预算但未触及硬上限的可保留并提示区间；无合适商品时再澄清，不自设浮动比例|
|期望区间（如“7000–10000 元”）|优先选 `price_max ≤ 10000`；低于 7000 且满足用途也可考虑（除非明确不低于 7000）；需要超过 10000 时先澄清|
|目标加硬上限（如“9000 左右，最多 11000”）|9000 为目标、11000 为硬上限；优先 9000 以内，9000–11000 可推荐但须说明价差与取舍；`price_min > 11000` 排除，跨 11000 判 `UNKNOWN`|

带有颜色或地区条件价备注的商品，展示价格时一并提示；价格排序统一按区间上限 `price_max` 从低到高。单价商品即 `price_min = price_max`；价格缺失或无效时判 `UNKNOWN`，不按 0 处理

**明确硬件与设备约束**

仅对用户实际提出并确认的项执行校验：内存与标称存储容量不小于要求、有效重量不大于要求，屏幕尺寸、操作系统等按对应字段规则核验。用户明确要求的属性缺少数据时判 `UNKNOWN`。

**硬条件汇总**

任一项 `FAIL` 则整体 `FAIL`（直接排除）；无 `FAIL` 但存在 `UNKNOWN` 则整体 `UNKNOWN`（待核验，不进入正式推荐）；全部已确认硬条件均 `PASS` 时，商品才进入 FR\-04。

### FR\-04｜游戏适配判断

**档位选择规则**

- 明确指定且本地已收录：按该档位校验。

- 明确指定但本地未收录（如《黑神话：悟空》推荐配置）：说明该档位无法验证及已收录档位，不编造要求也不默认降档；只有在剩余澄清额度内获得用户明确同意后，才改按已有档位继续。

- 未指定档位：默认采用已收录最低档（《原神》对应“支持配置”），结果中注明采用档位和项目口径。

- 提出具体画质或帧率目标：明确说明 V1\.0 不提供实测帧率或画质保证；在剩余额度内确认是否接受可验证的配置档位，未获接受前不宣称体验目标已满足。

**适配校验维度（共 6 项）**

|维度|判定规则与项目采用口径|
|---|---|
|操作系统|`Win11 64位` 满足 `Win10 64位` 最低门槛，有明确不兼容证据除外|
|CPU|项目采用口径（仅比对 `CPU Mark 综合分`）：商品 CPU 与目标档位基准 CPU 各自实测分对比，`商品 cpu_mark ≥ 基准 cpu_mark` 判 `PASS`，`<` 判 `FAIL`；任一侧在本地两份榜单均未收录或无法唯一匹配则判 `UNKNOWN`，不另行补数。官方列出“Intel 或 AMD”双分支时取较低分支基准分；《原神》泛称档位锁定代表型号，支持配置取 `Intel Core i5-6400`，推荐配置取 `Intel Core i7-7700`|
|GPU|先做独显准入（项目口径）：纯核显配置直接判 `FAIL`，配备独显（含独显\+核显）进入型号核验。再基于 `gpu-mark.csv` 各自实测 `g3d_mark` 对比：`商品 g3d_mark ≥ 基准 g3d_mark` 判 `PASS`，`<` 判 `FAIL`，缺分判 `UNKNOWN`。不得将台式机显卡分数套用到同名笔记本显卡。官方列多款并行显卡时，优先在独显分支中取较低 `g3d_mark` 作为基准分（若官方全为核显分支则取已收录较低分）|
|显存（VRAM）|商品显存容量不小于目标档位要求判 `PASS`，小于判 `FAIL`，缺失判 `UNKNOWN`。官方未单独列显存要求（如《原神》支持配置）时直接 `PASS`；官方按显卡分双分支列显存（如《黑神话：悟空》最低档 6GB/8GB）时，按项目口径取较低分支下限（`≥ 6GB`）|
|内存|按对应游戏、对应档位的内存要求比较容量|
|存储容量|按项目口径比较商品标称存储容量是否不小于游戏空间要求，忽略系统已占空间，不保证实际可用空间|

> 规则表官方备注中的指令集（`SSE2 / SSE4 / SSE4.2 / AVX`）、图形接口（`DirectX 11`）和“推荐 SSD”在商品表中未单独采集，这些项只作结果提示说明，不作为阻断推荐资格的 `UNKNOWN` 项。
> 
> 

**CPU / GPU 离线映射与边界**

商品目录和游戏要求中的 CPU / GPU 型号在数据构建期通过离线 ETL 清洗并写入静态映射表，运行时由程序直接读取分数进行判定和比较。未找到、无法唯一确认或缺分时标注“暂无法比较”，不猜测、不补分、也不按 0 分处理。PassMark 综合分仅作为配置符合性的项目采用口径和综合性能参考，同分不判优劣，不叠加核心数、频率或模型常识，展示时须注明项目口径，不能据此承诺实际画质、帧率或持续散热表现。

**多游戏汇总**

单游戏内任一维度 `FAIL` 则整体 `FAIL`，无 `FAIL` 但有 `UNKNOWN` 则整体 `UNKNOWN`，6 维全 `PASS` 则 `PASS`。多游戏场景下，所有必要游戏都必须 `PASS`（范围外必要游戏或未收录必要档位不能判整体通过）；非必要附加游戏不否决资格，但其不满足、未知或未覆盖状态须在结果中如实说明。

### FR\-05｜可信候选推荐与解释

只有来自本地目录、关键事实有效、硬条件 `PASS` 且全部必要游戏 `PASS` 的商品，才能由程序判定为合格候选，模型不能改动资格结论。

**排序与分批规则**

1. 先按 FR\-03 预算规则优先选出目标预算内的合格商品（较便宜且满足用途的商品不因未花满预算被排除；超目标预算但在硬上限内的商品须说明价差和取舍）。

2. 再按用户明确表达的软偏好和可靠事实筛选排序。

3. 预算和偏好都无法区分的候选，若该组全部商品都有 `cpu_mark` 分数，按 `cpu_mark` 从高到低排，同分依次按较低 `price_max`、目录固定顺序排。

4. 只有实际成功展示给用户的商品才计入已展示记录（失败不跳批）。无更多合格商品时提示“当前条件下的合格商品已全部展示”并保留最后一批。

**商品卡片展示规范**

正常返回正式推荐时只展示商品卡片，推荐理由、限制，直接放在卡片内，不另附重复的长段说明。

|顺序|卡片字段|展示要求|
|---|---|---|
|1|商品名称|品牌加完整型号，与配置共同唯一标识具体版本|
|2|参考价格|参考价或价格区间（元）及价格条件备注（如有），标注“参考价”|
|3|关键配置|CPU、GPU（含显存）、内存、存储（单位一致）；用户明确关心屏幕或重量时补充，未知项标“未知”|
|4|游戏适配|仅在有附加游戏或更高档位余量时才单列一行；否则则不单一展示，在标题行统一展示|
|5|亮点|1–2 条短句说明如何匹配需求及单款差异化取舍|
|6|限制|已知不足、未满足的软偏好和适用范围限制或短板，无须补充时可省略|
|7|比较选择|当前批次卡片的勾选框，选中 2–3 款后点击推荐区“比较”发起对比|

### FR\-06｜候选比较与商品事实追问

用户可通过两种方式发起比较（仅限当前批次 2–3 款，不支持跨批）：

- 点击勾选当前批次中的 2–3 款后点“比较”，少于 2 款不发起。

- 自然语言指定当前批次中的 2–3 款；未指定对象时默认比较当前批次全部商品。当前批次只有 1 款时说明该款适配情况、优点与限制，不伪造多款对比；用户指定其他批次、已失效或范围外商品时说明仅限当前批次，不擅自替换。

商品事实追问须引用具体配置版本的可靠数据，修改条件后旧比较结果失效。

对比结果用单张表格呈现，第一列为维度，后续每列对应一款具体配置，差异与建议直接写在表内，不另附重复长文：

|对比维度|展示口径|
|---|---|
|机型名称（表头）|展示品牌与具体型号版本（与商品卡片标题一致），底层按具体配置唯一标识，不混用同系列其他配置|
|价格|展示历史参考价或价格区间；仅在存在颜色、地区等条件价时附简短备注。|
|处理器|展示 CPU 型号与对应的 `cpu_mark` 性能参考分（界面展示为“性能分 X”，不展示后台榜单映射名）|
|显卡|展示显卡型号、显存容量与对应的 `g3d_mark` 性能参考分（界面展示为“性能分 X”，不展示后台榜单映射名）|
|内存|单独列行展示内存容量，各列单位一致|
|存储|单独列行展示标称存储容量，各列单位一致|
|其他关心属性（可不展示）|用户明确关心重量、屏幕尺寸等属性时按需增加对应行，单位一致，未知项明确标注“未知”|
|游戏适配（有差异时展示）|仅当所选机型存在适配差异时展示（如涉及非必要附加游戏，或各款满足不同配置档位）；若所选机型对必玩游戏满足同一档位且无附加游戏差异，不展示|
|主要不足|简短列明影响本次选购的已知短板、未满足的软偏好或条件价备注；无明显不足时标“—”|
|选择建议|放在表格最后一行，每款用 1–2 条短句说明相对当前需求的优势与取舍，不单凭某一项参数下结论|

**表底统一提示**：表格底部附一行轻量说明——“性能分越高综合性能越强，仅供参考；配置达标不代表实际画质与帧率表现。”

### FR\-07｜条件修改与重新评估

|变更类型|示例|处理方式|
|---|---|---|
|预算修改|“预算改成 12000”|保留原有约束性质（目标预算或硬边界），含义不明或冲突时先澄清|
|硬件条件修改|“内存至少 32GB”|更新对应硬件边界，重跑硬条件筛选|
|条件撤销|“重量不限制了”|移除该硬条件，重评此前被该条件排除的商品|
|游戏或档位修改|“改玩原神”“要推荐配置”|更新游戏或档位（未收录档位按 FR\-04 处理），重跑对应游戏适配|
|软偏好修改|“重量比性能重要”|按 FR\-05 重选展示候选与解释，复用已通过的硬条件和资格结论|

清空与保留的状态变化按流程图 3\.3 执行。候选发生变化时说明主要原因；澄清回复未再次改动条件时，继续完成原评估、不重复清空记录。

### FR\-08｜无法推荐与异常反馈

**异常处理规则**

|异常情况|判定条件|处理与结果|
|---|---|---|
|关键需求缺失|缺少影响筛选或必要适配的用户信息|在剩余额度内按 FR\-02 澄清（`R03`）；到限仍不足按 `R02` 说明|
|条件冲突|用户提出的条件无法同时成立|指出冲突并在剩余额度内确认；到限仍无法继续按 `R02` 说明，不自动修改|
|硬条件无匹配|目录商品均明确违反至少一项必要硬条件|说明目录无匹配及主要限制（`R02`）|
|游戏适配不满足|硬条件通过，但必要游戏适配明确 `FAIL`|排除对应商品；无其他合格候选时说明不满足原因（`R02`）|
|关键证据不足|无合格候选，且存在必要校验 `UNKNOWN` 的潜在候选|说明无法确认的具体字段或依据，不表述为目录无匹配（`R02`）|
|用户拒绝必要澄清|无法获得继续判断所需的关键信息|提前停问，说明无法可靠判断及原因（`R02`）|
|超出游戏或档位范围|必要游戏不在 4 款内，或指定档位未收录|说明支持范围，不默认降档；确认接受已有档位才继续，否则按 `R02` 说明|
|模型或处理失败、执行超限|必要处理未完成，或达到 60 秒上限|瞬时故障由 Harness 静默重试 1 次；仍失败报 `R04` 停止，不生成新正式推荐、不称无匹配，提供最多 1 次手动重试|

条件未变时的换批或比较失败，保留原本仍有效的当前批次；条件已变化后的重评失败，不恢复旧批次。正常读到的 `UNKNOWN` 或无匹配属于业务结论，不提供重试按钮。用户可以补充信息、放宽硬条件、更换游戏或档位、点击手动重试（最多 1 次）或重新发消息；Agent 可以给调整建议，但不能替用户确认或修改硬条件。

## 五、页面布局与展示要求

V1\.0 采用桌面端侧边浮窗形态：默认以网页侧边小按钮停靠，点击展开为独立选购小窗并隐藏侧边按钮（宽度满足 3 张卡片横向并排及 2–3 款对比表单页展示、不出现横向滚动），点击小窗右上角“—”可收起回侧边按钮。

|**页面区域**|**展示内容与职责**|
|---|---|
|顶部栏|窗口标题、任务状态标（仅在处理中、等待补充/确认、无法推荐、执行异常时显示，区分“等待用户”与“执行异常”）；右侧提供“重新开始”（默认首页隐藏）与收起图标按钮|
|当前条件摘要|固定在顶部栏下方，纯只读展示当前有效的目标游戏、预算、硬条件与软偏好|
|主对话区域|承接连续对话、澄清问答与异常反馈，直接内嵌推荐卡片与对比表。执行失败或超时（`R04`）时，在异常提示卡片内提供手动“重试”按钮（同一请求最多 1 次，用尽后不再显示）。默认首页（首次打开、刷新或重新开始）隐藏条件摘要与页底提示，在对话区展示用途、支持游戏列表及 1–2 句示例问法（点击仅填入输入框）|
|推荐商品区域|批次上方写明本批数量、必玩游戏档位及非帧率保证提示；最多 3 张卡片横向并排，单卡内部竖向排布：品牌型号与右上角勾选框、价格（含条件价时附备注）、核心配置、简短“亮点 / 限制”标签（有附加游戏差异时补充）。卡片下方提供“对比（含已选数量，选 2–3 款可用）”与“查看更多”|
|候选比较区域|发起比较后在对话内直接展示单张对比表（2–3 款单页呈现，游戏适配仅在有差异时列行），表底附性能分参考与非帧率保证说明；换批或改条件后清空|
|底部输入与统一提示|进入对话后在窗口最下方统一展示采集日期与非实时提示（“历史参考价（YYYY\-MM\-DD 采集），仅供参考，实际购买价格以销售平台为准。”）|

页面展示需满足以下要求：

- 不向用户界面暴露内部术语，也不暴露模型隐藏推理、运行日志、系统凭据或原始工具数据。

- 无法推荐时写明具体原因和下一步可选操作；执行异常或超时须与“目录无匹配”区分，业务原因无法推荐不显示重试按钮。

- 价格存在区间或颜色/地区条件价时在单卡与对比表中注明。

## 六、上线标准与评测衔接

### 6\.1 V1\.0 交付门槛

V1\.0 达到以下条件视为具备可验收状态：

1. **核心闭环跑通**：围绕 4 款支持游戏，完整跑通自然语言选购、必要澄清、候选推荐、当前批比较、事实追问、条件修改重评及异常反馈。

2. **四款游戏真实覆盖**：基于本地固定数据与真实来源，4 款支持游戏每款至少有 1 条明确档位的成功推荐用例（同一商品可复用于多个游戏）。

3. **数据与展示就绪**：4 份本地数据资产（商品目录、游戏规则、CPU 与 GPU 榜单）就绪且来源可追溯；非实时价格提示、项目采用口径说明和限制完整。

### 6\.2 验收阻断问题

以下问题直接影响产品可信度，出现任一项即判定 V1\.0 验收不通过）：

1. 正式推荐违反用户已确认的硬条件，或将硬条件、必要游戏适配为 `FAIL` / `UNKNOWN` 的商品放入正式推荐。

2. 编造商品参数、价格、游戏配置要求、性能分数或数据来源，或用确定性表述掩盖未知信息。

3. 将历史参考价表述为实时成交价，或将配置符合性、PassMark 分数表述为实际画质或帧率保证。

4. 用户修改有效条件后，仍继续沿用已失效的推荐资格、旧批次或旧比较结论。

5. 模型调用或处理失败、超时后，仍生成新的正式推荐，或将执行故障误报为“目录无匹配”。

    

### 6\.3 AI 效果验收与文档衔接

除功能可用外，V1\.0 需围绕 AI 导购的核心价值完成效果验收。具体测试集、样本量与通过阈值由 `05 Evaluation` 定义，本文明确验收维度与关注点：

|**验收维度**|**产品关注点**|
|---|---|
|任务完成质量|可完成任务能否给出可靠候选；无法推荐时能否说清原因和下一步操作|
|推荐可靠性与事实准确性|是否遵守硬条件、适配有依据、参数与来源记录一致|
|Agent 行动合理性|信息够时是否不乱问、缺关键项时能否问准、改条件能否复用有效信息|
|推荐解释可理解性|普通玩家能否看懂推荐理由、商品不足以及不同方案之间的取舍|
|执行效率|响应耗时、澄清轮次与调用开销是否在可接受范围内|
